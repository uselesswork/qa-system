# 第十一阶段 用户权限与会话持久化（后端与页面已接入）

> [返回项目说明](../README.md) · [上一阶段](第十阶段-持久化知识库底座.md)

## 一眼看懂本阶段

本阶段把第十阶段的持久化知识库和第七阶段的多轮对话接到同一套账号边界上。用户可注册、登录、退出；新建知识库自动写入当前用户 ID。知识库详情、文档、按库问答、全库问答和会话历史均由后端按用户过滤。聊天消息、改写问题、证据和模型元数据写入 MySQL，刷新页面或重建数据库连接后仍能读取和续问。前端不再把会话历史存进浏览器本地存储，而是在登录后加载服务端会话列表。

## 具体完成的工作

### 账号、Cookie 与 CSRF

`src/auth/service.py` 负责注册、密码核对和登录会话。用户名统一转小写，只接受 3～32 位英文字母、数字或下划线；密码长度限制为 12～128 字符。注册时只保存 Argon2 哈希，登录时用同一密码哈希实现校验，用户名不存在时也执行占位校验以减少明显的时序差异。会话令牌由安全随机数生成，数据库 `auth_sessions` 只存令牌摘要、用户 ID、CSRF 令牌和过期时间；退出时删除记录。

`app/api/auth.py` 设置 `HttpOnly`、`SameSite=Strict` Cookie。通过 HTTPS 访问时设置 `Secure`；本机 HTTP 开发模式不设置 `Secure`，因此不能把本地运行方式直接当作公网安全部署方案。页面仅在 JavaScript 内存中持有从登录响应或 `/auth/me` 获取的 CSRF 令牌，写请求放在 `X-CSRF-Token` 头中。刷新页面后通过 Cookie 和 `/auth/me` 恢复登录态，不把令牌写入 `localStorage`。登录与 `/auth/me` 响应带 `Cache-Control: no-store`。

目前没有注册邀请、邮箱验证、找回密码、登录限流、账号封禁和管理员角色；适合受信任的本机开发演示，不建议直接暴露到公网。后续安全加固阶段应补限流、代理/HTTPS 配置、会话清理和审计。

### 旧知识库归属与检索隔离

`knowledge_bases.owner_id` 允许为空是为了无损迁移既有演示数据和手动上传数据。用户明确选择“先保留未归属”：迁移不回填所有者，不把它们交给第一个注册账号。普通账号创建的新库自动归自己；列表只显示自己的库；详情、文档列表、上传、重建、删除、按库问答都在服务端核对归属。未归属或别人的库对当前用户统一表现为 404。后续若要接管旧库，必须由操作者明确指定目标用户和知识库，再设计一次性管理迁移；当前不提供自助认领接口。

旧版 `/ask`、`/chat`、`/ask/stream` 曾直接查询启动时加载的固定示例索引，单纯加登录仍会暴露公共资料。本阶段把这三个入口也改成按当前用户所有 `ready` 文档 ID 过滤 Qdrant；应用启动不再把 `data/multi_document_examples` 示例文档向量化。`POST /knowledge-bases/{id}/ask` 仍额外按库 ID 和 `ready` 文档 ID 双重过滤。没有已索引文档的账号不会检索到他人的或未归属的片段。`data/multi_document_examples` 仅保留为实验素材和演示数据播种来源；播种文档是 `pending`，不会自动成为可检索资料。

隔离依赖关系库中的所有权和文档状态作为权威来源，Qdrant 点 payload 的文档 ID 只用于执行已授权的过滤。证据来自本次过滤后的检索结果；保存的历史证据只有该会话的所有者可读。当前单库问答和全库聊天同时存在，页面主路径是全库聊天。

### MySQL 会话与完整轮次

`chat_sessions` 保存用户 ID、标题及时间；`chat_messages` 按 `session_id` 和唯一 `ordinal` 排序，保存角色、正文、助手侧改写查询、证据 JSON 和元数据 JSON。新建会话先写入空标题；首次成功问答用问题前 80 个字符形成标题。`src/chat/repository.py` 每次先核对会话所有者，再读取或写入消息。一次问答先读取最近 10 轮历史交给查询改写器，复用 RAG 问答链，成功后在单个数据库事务中同时写入用户消息和助手消息。模型出错时不写半轮；数据库事务失败时不把本轮标为成功。

会话 ID 由后端生成，不能再由浏览器任意指定。旧 `/chat` 路径仍接受 `session_id` 和 `message`，但要求该 ID 已由当前用户通过 `POST /chat/sessions` 创建；不会把旧浏览器 `localStorage` 历史自动迁入数据库。没有用户归属的旧内存会话不可恢复。页面加载时清理旧 `rag-chat-session`、`rag-chat-history` 两个本地存储键。

本阶段没有引入 Redis：MySQL 已是登录会话与聊天历史的持久化来源，Redis 停机不会影响本阶段数据。第十二阶段若引入 Redis 队列或缓存，应保持 MySQL 为聊天历史权威来源。并发对同一会话发多条消息、多个 Web worker 共用 Qdrant 本地目录和长期消息量尚未专项压测。

### 前端流程

打开首页先调用 `/auth/me`。未登录显示登录/注册表单；登录后显示会话列表和问答区。新对话调用 `POST /chat/sessions`，点击历史列表调用 `GET /chat/sessions/{id}`，发送消息调用 `POST /chat/sessions/{id}/messages`。接口返回后更新消息、证据和会话标题；刷新或重新打开页面从服务端读取，不依赖浏览器缓存。页面用 `textContent` 渲染回答和证据，不将模型输出当 HTML 注入。

当前还没有知识库创建、上传和文档管理页面；需用 `/docs` 或 API 客户端创建自己的库并上传文件后，再在首页问答。首页主路径会检索当前账号下所有已索引文档。要严格限定单个知识库时，使用 `/knowledge-bases/{id}/ask`。页面没有流式聊天、上传进度或删除会话按钮。

## HTTP 接口与权限

| 方法与路径 | 作用 | 要求 |
| --- | --- | --- |
| `POST /auth/register` | 创建账号 | 无 Cookie；JSON `username`、`password` |
| `POST /auth/login` | 核对密码、写登录 Cookie、返回 CSRF 令牌 | 无 Cookie；JSON 凭证 |
| `GET /auth/me` | 取当前用户和 CSRF 令牌 | 登录 Cookie |
| `POST /auth/logout` | 删除会话并清 Cookie | 登录 Cookie + CSRF |
| `POST /chat/sessions` | 创建空会话 | 登录 Cookie + CSRF |
| `GET /chat/sessions` | 当前用户的会话列表 | 登录 Cookie |
| `GET /chat/sessions/{id}` | 当前用户的消息、证据和改写历史 | 登录 Cookie；非本人 404 |
| `POST /chat/sessions/{id}/messages` | 续问并持久化一轮 | 登录 Cookie + CSRF；JSON `message` |
| `POST /chat` | 兼容旧路径，要求预先创建且属于自己的 `session_id` | 登录 Cookie + CSRF |
| `POST /ask`、`GET /ask/stream` | 单轮/流式问答，只检索本人所有已索引文档 | 登录 Cookie + CSRF |
| `/knowledge-bases...` | 第十阶段的知识库接口 | 所有接口要求登录；写入及问答要求 CSRF，并核对知识库归属 |

Cookie 由浏览器自动携带；用 `/docs` 或 HTTP 客户端调写接口时，先登录，再把登录响应中的 `csrf_token` 复制到 `X-CSRF-Token` 请求头。`POST /knowledge-bases/{id}/documents/{document_id}/reindex` 中的两个 ID 分别是知识库和文档 ID，不可省略。未登录返回 401，CSRF 不符返回 403，非本人知识库或会话返回 404。

## 验证与限制

从根目录运行 `.\.venv\Scripts\python.exe -m pytest -q`，本阶段结果为 **29 passed**。测试使用临时 SQLite、临时 Qdrant、假 Embedding/LLM 或假 RAG，不调用真实模型或真实 MySQL；覆盖未登录、双账号隔离、未归属库隐藏、非本人访问、CSRF、重启后同一 Cookie/会话恢复、证据读取、向量过滤、退出以及模型错误不写入半轮。迁移测试在临时 SQLite 执行升级、Alembic 检查和降级。

本机真实 MySQL `qa_system` 从 `0001_initial` 升级到 `0002_auth_and_chat`，升级后核对：知识库总数 6，`owner_id IS NULL` 数量 6，用户数 0。没有改写或删除这些旧知识库。尚未使用真实模型和浏览器手工完成“注册 → 创建私有库 → 上传 → 问答 → 续问 → 刷新恢复”的端到端验收，也没有执行 Redis 或 Docker 验证。阶段 12 继续处理同步索引的耗时、失败重试和任务状态；阶段 15 处理限流、恶意输入和更完整的安全测试。
