# 第四阶段 重排与语义切分

> 对应原模块 9～10 · [返回项目说明](../README.md) · [上一阶段](第三阶段-回答生成与系统编排.md) · [下一阶段](第五阶段-答案与证据聚合.md)

## 一眼看懂本阶段

这阶段增加了两种质量控制：候选片段在进入 Prompt 前再次排序，以及根据 Markdown 标题决定片段边界。重排当前确实接入 Web；标题切分器虽然也被组装进 Web，但本轮核对发现它在当前代码中没有按预期匹配普通标题，实际走了长度切分回退。

| 项目 | 本阶段结果 |
| --- | --- |
| 目标 | 减少切分破坏语义、以及召回结果顺序不理想的问题 |
| 输入 | 原始文档和召回候选片段 |
| 输出 | 更合适的片段边界、经过二次排序的候选列表 |
| 当前 Web 状态 | Embedding 重排已接入；标题切分器已接入但本轮最小样本未生效 |

## 具体完成的工作

### Embedding 重排

`EmbeddingReranker` 在初次召回之后使用问题向量与候选向量重新计算余弦相似度、排序并截断到目标 Top K。RAGCore 为粗排前扩大召回数量，给二次排序留出候选空间。它仍使用与检索接近的语义信号，所以不能解决“片段谈论同一主题、却没有真正回答问题”的所有情况。

### 标题感知切分

`SemanticSplitter` 对 `file_type=md` 的文档先调用 `HeadingSemanticSplitter`；若没有得到片段，回退到第一阶段的 `TextSplitter`，其他格式直接使用长度切分。这是代码设计意图。当前 `HeadingSemanticSplitter.HEADING_PATTERN` 的原始字符串把 `\s` 写成了双反斜杠，未匹配普通 `# Title`；Web 组装还会先用 `TextCleaner` 折叠换行。两处共同导致现有 Web 路径不能可靠按 Markdown 标题切分。

## 数据流与对比实验

```text
设计：Markdown → 标题切分（失败时回退长度切分）→ Embedding → 召回
实际核对：# Title → 标题正则未命中 → 长度切分
问答：初始召回最多 10 片段 → Embedding 重排 → 最多 5 片段
```

原模块 9 比较有无重排：初始候选只有少量片段、两层又使用相似向量逻辑时，排序几乎不变；加入干扰片段后，部分案例的答案片段上升。模块 10 把普通长度切分和语义切分与有无重排交叉比较，观察到部分含噪声示例中重排有帮助。结论应限定在这些示例，不能推断语义切分或重排在任意资料集上都提高准确率。

| 原实验组合 | 原记录的主要观察 | 现在应如何解读 |
| --- | --- | --- |
| 普通切分、不重排 | 前排片段可能混有噪声和答案 | 基线示例，非总体质量指标 |
| 普通切分、Embedding 重排 | 部分示例把更有用的片段排到前面 | 说明候选空间和噪声设计会影响重排效果 |
| 标题切分、不重排 | 原截图中与普通切分差异有限 | 当前代码的标题识别反例要求重新验证该组合 |
| 标题切分、Embedding 重排 | 原截图中答案片段排序较靠前 | 不能据此断言当前 Web 仍有同样效果 |

检索和重排使用相近的余弦逻辑时，同一批片段重新打分可能不会改变顺序；原模块 9 对这一现象给出了合理解释。要判断语义切分是否真的改善结果，需要先修复标题识别、保留清洗前的标题换行，再用相同问题和标注片段重新比较。

## 验证与限制

本轮对 `Document(content='# Title\nBody text', metadata={'file_type':'md'})` 运行 `SemanticSplitter`，结果只有回退片段，没有 `semantic=heading` 或 `heading` 元数据。原模块 10 的截图只能反映当时的实验记录，不能覆盖当前代码的最小反例。PDF 和 TXT 不会按章节语义解析；Embedding 重排仍无法直接检验事实支持度。第五阶段的证据聚合与第八阶段的可选细排处理的是另外两个位置的问题。
