# 第八阶段 答案感知重排

> 对应原模块 16 · [返回项目说明](../README.md) · [上一阶段](第七阶段-多轮对话.md) · [下一阶段](第九阶段-工程基线与代码重构.md)

## 一眼看懂本阶段

这一阶段在 Embedding 粗排之后增加可选的“证据支持度”细排：先生成草稿答案，再让模型逐条判断候选片段是否提供直接支持。它与第五阶段最终证据聚合不同；当前 Web 组装没有开启这条细排分支。

| 项目 | 本阶段结果 |
| --- | --- |
| 目标 | 在“与问题相近”之外，判断候选片段对草稿答案是否有支持作用 |
| 输入 | 问题、草稿答案、初步召回的候选片段 |
| 输出 | 按支持度重新排序的候选列表 |
| 接入状态 | `RAGCore` 有可选开关；当前 `app/rag_app.py` 未开启 |

这一阶段探索的是检索后的细排，而第五阶段的聚合负责综合回答与挑选最终展示的证据。两者都涉及“答案感知”，但位于不同位置，输出分数含义也不同。

## 具体完成的工作

`AnswerAwareReranker` 接收问题和草稿答案，对每个候选片段计算支持度。`RAGCore` 在 `enable_answer_aware=True` 时，先用当前候选构造草稿 Prompt 并生成草稿答案，再执行这层细排，然后才进入聚合和最终生成。普通回答与流式回答共用这条检索/细排路径，不会出现两种接口使用不同候选的情况。这个细排需要异步调用模型，不再继承只约定同步 `rerank()` 的基础 Embedding 重排接口，也不再接收实际上未使用的 `query_vector` 参数。开关为 `False` 时跳过这段额外流程。原模块用含有关键词堆砌、部分正确、信息分散的对抗文档，观察三轮问答中细排前后的候选得分。

## 文件与职责

| 文件 | 作用 |
| --- | --- |
| `src/rerankers/answer_aware_reranker.py` | 对候选片段计算答案支持度并排序 |
| `src/rag/rag_core.py` | 通过 `enable_answer_aware` 控制细排位置 |
| `src/test/test_chat_multiturn.py` | 多轮实验输入与观察 |
| `app/rag_app.py` | 当前 Web 组装；没有设置该开关 |

## 数据流与分数解释

```text
召回候选 → Embedding 粗排 → 草稿答案 → 答案感知细排
→ 可选证据聚合 → 最终回答与展示证据
```

| 位置 | 分数表示什么 | 能否与其他阶段直接比较 |
| --- | --- | --- |
| Embedding 粗排 | 问题与片段的语义相似度 | 不能当答案准确率 |
| 答案感知细排 | 片段对草稿答案的支持度 | 与粗排分数不是同一含义 |
| 证据聚合 | 片段对最终综合证据的贡献 | 与前两种分数不能直接求提升率 |

`AnswerAwareReranker._score_chunk()` 给模型三档评分说明：1.0 为明确支持，0.5 为弱或间接支持，0.0 为仅同主题或无关。代码直接把模型文本转成 `float`，解析失败时给 0.0；成功解析的数值没有范围裁剪。`rerank()` 逐片段等待模型调用，排序后截断到 Top K。

原模块的对抗场景包含关键词高度重合却无有效解释的片段、只提供部分解释的片段，以及答案分散在不同文档的片段。粗排主要判断语义接近；细排的提示词明确要求“因果解释、事实证据或直接论证”，试图把主题相近但不支撑草稿答案的片段往后放。细排使用的是模型判断，错误的草稿答案可能反过来误导支持度判断。

## 开关和实验使用

`RAGCore` 构造参数 `enable_answer_aware` 默认为 `False`。开启后在粗排后生成草稿答案并细排，再进入聚合与最终生成。当前 `app/rag_app.py` 没有传入 `True`，所以网页的证据分数来自聚合器，而不是这里的支持度分数。原模块的多轮实验脚本单独构造开启该开关的 RAGCore。

## 验证与限制

原 README 曾把细排前后平均分数写成“提升”，但三种分数不是统一量纲，因此不能把数值差解释为准确率提高。无密钥回归已检查普通和流式分支都会执行同一细排步骤；没有真实模型复跑，历史实验只说明机制在选定案例中改变了片段评分。要证明质量收益，需要固定数据集、人工标注证据和统一评价指标。额外草稿生成与逐片段评估增加延迟及费用，也存在模型误评分或返回越界数值的风险。
