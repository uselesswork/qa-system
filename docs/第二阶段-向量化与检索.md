# 第二阶段 向量化与检索

> 对应原模块 3～5 · [返回项目说明](../README.md) · [上一阶段](第一阶段-文档加载与切分.md) · [下一阶段](第三阶段-回答生成与系统编排.md)

## 一眼看懂本阶段

这阶段的可见结果是：给一个问题，检索器返回若干相关片段和相似度分数。文档先批量向量化并加入内存库；提问时只向量化问题，再从已保存向量中取前 K 个候选。检索不直接生成自然语言答案。

| 项目 | 本阶段结果 |
| --- | --- |
| 目标 | 从文档片段中找出与问题语义接近的候选内容 |
| 输入 | 第一阶段的 `TextChunk` 与用户问题 |
| 输出 | 按相似度排序的 `SearchResult(chunk, score)` |
| 主要组件 | OpenAI Embedding、进程内向量库、Top K 检索器 |
| 数据保存 | 仅进程内存；重启后需要重建索引 |

本阶段把文档侧和问题侧放到同一向量空间，再通过余弦相似度召回候选片段。它解决“先找哪些内容”，尚不判断候选是否足以回答问题。

## 具体完成的工作

### 文档与问题向量化

`OpenAIEmbedding.embed()` 批量发送片段文本，返回带向量的 `EmbeddedChunk`，并在元数据里记录 Embedding 模型名和维度。`embed_texts()` 用于查询侧及后续重排、聚合。当前默认模型名为 `text-embedding-3-small`，调用需要有效的 OpenAI 配置。

### 内存向量检索

`InMemoryVectorStore.add()` 追加片段；`search()` 遍历存储内容，计算问题向量与每个片段向量的余弦相似度，按分数降序取前 `top_k`。`SimpleRetriever.retrieve()` 先把问题转为向量，再调用存储层搜索。新增的 `retrieve_with_vector()` 同时返回候选与这次已经计算的问题向量，供 Embedding 重排复用，避免同一轮问答为粗排再次请求问题 Embedding。其他检索器只实现原 `retrieve()` 时，基础接口会提供兼容回退。Embedding、VectorStore 和 Retriever 仍保持分层职责。

## 文件与职责

| 文件 | 作用 |

## 数据流和结果含义

```text
TextChunk 列表 → 批量 Embedding → EmbeddedChunk → InMemoryVectorStore
用户问题 → embed_texts() → 查询向量 → search(top_k) → SearchResult 列表
```

`SearchResult` 中的 `chunk` 是带向量和元数据的片段，`score` 是本次余弦计算结果；`RetrievalBatch` 额外保存 `query_vector`，不是另一个搜索结果结构。当前 `RAGCore` 先召回 `top_k × 2` 个候选，再交给重排器截断；应用配置 `top_k=5`，因此会先取最多 10 个候选供下一阶段处理。文档批量 Embedding 在应用启动阶段完成，不是每次提问都重新向量化整个文档集。

## 模型配置和本地使用

`OpenAIEmbedding` 默认使用 `text-embedding-3-small`，读取 `OPENAI_API_KEY`。`src/test/test_embedding.py`、`test_retriever.py` 会调用外部 Embedding 服务；`test_vectorstore.py` 则需先检查其所用夹具和调用路径，再决定是否运行。没有密钥时可以阅读或用假向量隔离验证内存库，但不能把这种验证写成真实检索联调。

## 验证与限制

原模块分别展示了向量化、入库和查询输出；本次用假向量验证检索加重排时问题只向量化一次，并验证零向量的余弦分数为 0，没有调用真实 Embedding 服务。这里的 `score` 不能理解为事实正确率或答案支持概率。内存库采用全量遍历，并以 `add()` 追加数据，没有持久化、增量去重、跨用户隔离或大规模索引；当前应用每次启动都重新计算示例资料向量。
