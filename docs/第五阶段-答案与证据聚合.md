# 第五阶段 答案与证据聚合

> 对应原模块 11～12 · [返回项目说明](../README.md) · [上一阶段](第四阶段-重排与语义切分.md) · [下一阶段](第六阶段-问答接口与前端.md)

## 一眼看懂本阶段

当前 Web 组装使用跨文档 `AnswerAwareAggregator`：先逐片段分析，再合成答案，最后选出最多 3 条证据。页面展示的是聚合挑出的依据，不是全部初始召回片段。

| 项目 | 本阶段结果 |
| --- | --- |
| 目标 | 综合多个候选片段回答问题，并把关键依据随回答返回 |
| 输入 | 用户问题和重排后的 `SearchResult` 列表 |
| 输出 | `AggregatedAnswer`，包含回答与 `EvidenceChunk` 列表 |
| 当前 Web 状态 | `app/rag_app.py` 组装了 `answer_multitude_aggregator.py` 中的 `AnswerAwareAggregator` |

普通 RAG 可以给模型一组片段，却未必明确哪个片段支撑最终结论。本阶段将“形成回答”和“选择证据”放到同一聚合流程，尤其关注答案分散在多个文档的情况。

## 具体完成的工作

### 聚合结果结构

`EvidenceChunk` 包含排序、分数、来源、`chunk_id` 和内容；`AggregatedAnswer` 包含综合回答和证据列表。`RAGResult` 增加 `evidence_chunks`，供接口与页面展示。这个结构把“检索到的全部候选”与“最终展示的依据”区分开。

### 简单聚合与答案感知聚合

项目保留简单聚合方案作对照。当前 Web 使用的 `AnswerAwareAggregator` 会逐片段调用模型分析相关性、独特信息和可靠性，再结合这些分析生成综合回答；之后通过答案及片段的向量关系给证据排序，选择有限数量的依据。它意在压低关键词堆砌或内容空洞片段的影响，并允许不同文档的互补信息共同支持一个回答。

`simple_aggregator.py` 直接把排序靠前的片段转为证据列表，返回类型与当前 `RAGCore` 所期待的 `AggregatedAnswer` 不同，不能不加适配就替换当前 Web 聚合器。当前跨文档实现会对查询和综合答案再计算向量，用答案相似度、问题相似度、内容信息密度和跨片段共识项计算证据分数；这属于启发式排序，不是独立事实验证。

## 数据流和分数含义

```text
候选片段 → 逐片段分析 → 综合答案 → 证据评分与排序
→ AggregatedAnswer → RAGResult → API 的 answer/evidence 字段
```

结果中的 `rank` 是聚合后的名次，`score` 是加权值，`source` 与 `chunk_id` 来自片段元数据。`app/rag_app.py` 将 `max_chunks` 设为 3。`POST /ask` 和 `POST /chat` 把这些片段序列化为 `evidence` 数组；页面显示名次、分数、来源和正文。

| 评分组成 | 当前跨文档实现中的作用 | 需要注意 |
| --- | --- | --- |
| 答案与片段向量相似度，权重 0.45 | 倾向于挑出贴近综合答案的片段 | 综合答案本身若错误，会影响排序 |
| 问题与片段向量相似度，权重 0.25 | 保留与原问题的联系 | 高相似不代表有事实支撑 |
| 信息密度，权重 0.15 | 惩罚重复词较多、信息量低的文本 | 基于空白分词，对中文文本只是粗略启发式 |
| 跨文档共识项，权重 0.15 | 利用各片段与综合答案的相对一致性 | 不是独立来源真实性检验 |

这也解释了为什么最终证据 `score` 可能超过 1：信息密度项并非限制在 0～1 的概率。原模块 16 的答案感知细排分数与这里的聚合分数不能直接相减或计算百分比提升。

## 接口和实验资料

`src/test/test_answer_aggregator.py` 与 `test_multidoc_comparison.py` 是原有实验入口，`data/model12/` 是当前 Web 使用的多文档示例。原实验用关键词堆砌、部分正确和答案分散的片段观察聚合结果，具体观察已概述在本阶段。聚合会对每个候选做模型分析，再生成综合答案和向量；候选数越多，调用量越高。

## 验证与限制

原模块 11、12 用无聚合与有聚合的示例及对抗文档比较回答和证据。本轮没有重新调用真实模型；旧结果是案例观察，不是统一样本集上的质量证明。模型生成的“可靠性分析”不等于事实核验。证据分数是聚合权重，可能与余弦相似度不在同一量纲，不能直接当成正确概率。
