## 启动异步模式

完整的 Windows 启动、检查和停止命令见[Redis 与 Docker 启动步骤](Redis与Docker启动步骤.md)。

1. 安装 Python 依赖：`.\.venv\Scripts\python.exe -m pip install "celery[redis]>=5.5,<5.7" "packaging<26"`。
2. 启动 Docker Desktop 后运行 `docker compose -f compose.ingestion.yaml up -d`，提供 Redis `6379` 和 Qdrant `6333`。也可使用已有的独立 Redis、Qdrant 服务。
3. 在本机 `.env` 设置 `REDIS_URL=redis://127.0.0.1:6379/0` 和 `QDRANT_URL=http://127.0.0.1:6333`。Web 和 worker 必须连接同一个 Qdrant 服务。本地文件模式 `data/qdrant/` 不能跨进程共享。
4. 升级数据库：`.\.venv\Scripts\python.exe -m alembic upgrade head`。
5. 分别运行 Web、worker、beat：

   ```powershell
   .\.venv\Scripts\python.exe -m uvicorn app.main:app --host 127.0.0.1 --port 8090
   .\.venv\Scripts\celery.exe -A src.tasks.ingest:celery_app worker --pool=solo --loglevel=info
   .\.venv\Scripts\celery.exe -A src.tasks.ingest:celery_app beat --loglevel=info
   ```

切换到独立 Qdrant 后，旧 `data/qdrant/` 中的向量不会自动迁移。在页面对已有 `ready` 文档点“重建索引”，完成后再验证问答。

## 状态与接口

- `POST /knowledge-bases/{id}/documents`：异步模式返回 `202`、任务 ID、文档 ID、`pending`。未配置异步模式时保留旧 `201` 同步响应。
- `GET /knowledge-bases/{id}/tasks/{task_id}`：只允许库所有者查询 `pending/indexing/ready/failed`、尝试次数和错误。
- `POST /knowledge-bases/{id}/tasks/{task_id}/retry`：只允许本人重新提交失败或仍排队的任务。
- `POST /knowledge-bases/{id}/documents/{document_id}/reindex`：异步模式返回新任务；同步模式保持旧行为。
- `GET /knowledge-bases/{id}/documents`：每份文档附最近任务 ID，页面每 3 秒刷新正在排队或索引的文档。

Celery 使用晚确认和单任务预取。beat 每分钟重新发布数据库中的 `pending` 任务；超过 30 分钟仍为 `indexing` 的任务视作 worker 中断并重新排队。任务 ID 保存在 MySQL，Redis 消息丢失后仍可从数据库恢复。重建前按文档 ID 清理 Qdrant 向量，避免 worker 中断后的残留点被重复使用。

## 本机浏览器验收（2026-11-16）

使用独立测试账号 `qa_browser_1116` 和知识库 `浏览器验收_20261116`，未改动原账号的知识库。在浏览器上传 [`browser-qa-20261116.md`](../data/acceptance/browser-qa-20261116.md) 后，页面先显示“待索引”，随后显示“已索引”。保持联网搜索关闭，提问“验收编号是多少？请只依据当前知识库回答”，页面回答 **7143**，并显示 **1 条检索依据**。这验证了上传、后台索引、页面状态刷新、知识库检索与真实模型回答的完整链路。浏览器显示了排队状态；本次没有单独抓取上传响应包核对 HTTP `202`，该响应由离线接口测试覆盖。

故障演练时短暂停止 `qdrant` 容器，再从浏览器上传 [`browser-retry-20261116.md`](../data/acceptance/browser-retry-20261116.md)。页面显示“索引失败”和“重试索引”，失败信息包含 Qdrant 请求的 `502 Bad Gateway`。重新启动 Qdrant 后点击“重试索引”，页面变为“已索引”；随后提问“故障恢复的验收编号是多少”，页面回答 **8625**，显示 **1 条检索依据**。演练结束后 `docker compose -f compose.ingestion.yaml ps` 显示 Qdrant、Redis 均为 `Up`。测试账号、知识库、两份文件和问答会话保留，便于复查。
