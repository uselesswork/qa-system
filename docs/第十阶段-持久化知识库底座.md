## 具体完成的工作

### 三张表的职责

`knowledge_bases` 记录知识库 UUID、名称、描述及创建/更新时间。现阶段没有账号体系，因此不声称已经按用户隔离；阶段 11 加账号时需专门迁移所有权结构。

`documents` 属于一个知识库，记录原文件名、格式、存储键、SHA-256、字节数、索引状态、错误信息和时间。状态限于 `pending`、`indexing`、`ready`、`failed`。同一知识库内 `(knowledge_base_id, sha256)` 唯一；相同内容再次上传返回 409，相同内容在不同知识库可以分别入库。新上传文件使用 UUID 文件名保存；旧播种资料的 `storage_key` 指向仓库样例，不会被新服务当成可重建的上传文件。

`chunks` 属于一个文档，记录片段 UUID、文档内序号、正文、标题、PDF 页码、字符区间和创建时间。同一文档的 `ordinal` 唯一。Qdrant 点 ID 复用 `chunks.id`，点 payload 带知识库和文档 ID。外键采用删除级联；直接在数据库删除知识库**不会自动清理 Qdrant**，因此当前接口只提供文档级删除，不提供危险的知识库级联删除。

### 连接与迁移

`src/db/session.py` 在实际调用时才从 `.env`/进程环境读取 `DATABASE_URL`，导入模块不会连接数据库；缺失配置会明确报错。生产连接示例使用 `mysql+pymysql` 和 `utf8mb4`。`alembic.ini` 不保存连接串，`migrations/env.py` 直接读取同一配置。初始迁移创建三张表、唯一约束、状态与非负值检查及常用索引。后续结构变更应新增迁移，不修改已应用的初始迁移。

MySQL 数据库本身需由有权限的本地管理员先创建；`scripts/create_database.sql` 只提供可复用的 `qa_system` 建库语句，不包含密码或用户凭据。用户创建数据库并在被 Git 忽略的 `.env` 配置本机连接后，本轮执行了 `alembic upgrade head`，确认版本为 `0001_initial`，三张业务表和 `alembic_version` 均存在。没有把连接密码写进代码或文档。

### 可重复的演示数据

`scripts/seed_demo_data.py` 读取仓库现有的 `data/multi_document_examples/doc1.md`～`doc6.md`，通过与 Web 相同的 Markdown 清洗和标题切分流程生成片段。六份资料分到 5 个知识库：原有的 RAG 演示资料保留 `doc1`、`doc2`，其余四个库分别对应候选片段差异、关键词噪声、重排目标和失败机制案例。每个库的 `description` 概述所含资料及未建向量索引的状态；再次播种只补全空描述，不覆盖非空的自定义描述。知识库、文档及片段使用确定性 UUID；原有知识库、`doc1`、`doc2` 的 ID 和归属不变。文档记录实际文件 SHA-256、大小和相对路径。播种在单个数据库事务中完成：输入缺失或已播种内容与当前文件冲突时停止，不覆盖已有记录。空库首次运行新增 5 个知识库、6 份文档、6 个片段；在原先 `1/2/2` 数据基础上升级时新增 `4/4/4`；再次运行不新增业务记录。旧版 `storage_key` 为 `data/model12/...` 的演示记录在重跑脚本时只更新为新目录，不改写正文、哈希、ID 或用户归属。

2026-11-12 目录更名后，本机重跑播种脚本，仅更新 6 条旧资料的 `storage_key`；旧目录路径剩余 0 条，新路径 6 条，文档总数仍为 7（其中 1 条为后续手动上传）。

这六份文档保留 `pending` 状态，因为尚未写入 Qdrant。数据库中的片段正文仅供后续服务开发和关系查询验证，**不能据此称当前网页已支持持久化知识库检索**。

### 上传、索引与查询链路

`app/api/knowledge.py` 提供独立于旧 `/ask`、`/chat` 的知识库接口。上传只接受 `.md`、`.txt` 和可提取文字的 `.pdf`，单文件最多 10 MiB；文件名只取末段，磁盘文件以新 UUID 命名，保存在被 Git 忽略的 `data/uploads/`。解析失败或没有可提取文字返回 422，重复 SHA-256 返回 409。扫描 PDF 没有 OCR，不会伪装成索引成功。

同步上传的顺序是：检查知识库和重复内容 → 保存原文件 → 清洗、切分 → 数据库写入 `pending` 文档 → 调用 Embedding → Qdrant upsert → 同一数据库事务写入片段并改为 `ready`。Qdrant 本地数据默认位于被 Git 忽略的 `data/qdrant/`。片段 UUID 同时作为 Qdrant 点 ID；同一集合中 payload 保存 `knowledge_base_id`、`document_id`、来源和正文。按库问答先从数据库取得该库的 `ready` 文档 ID，再由 Qdrant 同时按库 ID 和文档 ID 过滤，最后复用原有 RAG 核心完成生成与证据聚合。未索引的播种资料不会误入结果。

Embedding 或向量写入失败时，文档保持 `failed`，不会被问答检索；数据库写片段失败时尝试清理已写向量。删除文档先撤销 `ready` 状态，再删向量、数据库记录和上传文件；向量删除失败时保留 `pending` 文档以便重试。重建索引从上传原文件重新解析和写向量，适用于失败记录。跨 MySQL 和 Qdrant 不能形成一个原子事务，补偿失败仍可能留下孤儿向量；查询的 `ready` 过滤阻止它们参与回答，后续仍需加入定期对账和任务重试。当前同步实现适合小文件开发，不适合多工作进程或高并发上传。

### HTTP 接口

| 方法与路径 | 输入与结果 |
| --- | --- |
| `POST /knowledge-bases` | JSON `name`、可选 `description`；返回新知识库 |
| `GET /knowledge-bases`、`GET /knowledge-bases/{id}` | 列表和详情 |
| `POST /knowledge-bases/{id}/documents` | multipart 字段 `file`；成功时文档 `ready` |
| `GET /knowledge-bases/{id}/documents` | 文档列表、索引状态与失败类型 |
| `POST /knowledge-bases/{id}/documents/{document_id}/reindex` | 使用已保存原文件重建索引 |
| `DELETE /knowledge-bases/{id}/documents/{document_id}` | 先停用检索，再删除向量、关系记录和文件 |
| `POST /knowledge-bases/{id}/ask` | JSON `query`；只使用指定知识库的 `ready` 文档 |

目前没有用户身份或权限校验，所有知识库对调用方可见。接口只应在受信任的本机环境使用；不能部署为公开服务。新接口尚未接入首页 UI，也没有会话持久化。由于旧 RAG 在应用启动时仍会索引固定示例文档，启动服务仍需要有效的 `OPENAI_API_KEY` 和可用模型接口。

## 本机建库与验证

依赖安装命令只在根 README 维护，不新增 requirements 文件。全新环境仍须先用 MySQL 管理员执行 `scripts/create_database.sql`，把连接串放入被 Git 忽略的根目录 `.env`；不要将密码写在命令参数或聊天消息里。随后从仓库根目录运行 `python -m alembic upgrade head`，再运行 `python -m scripts.seed_demo_data`。播种脚本可重复执行，但如果已有同 ID 演示记录与本地样例内容冲突会报错，不会重写它。

本机真实 MySQL 在播种完成时的核对结果：数据库为 `qa_system`，迁移版本 `0001_initial`，知识库/文档/片段行数为 `5/6/6`；5 个知识库均有非空描述，每个知识库至少有一份文档，六份文档均为 `pending`。后续手动上传会改变总行数。2026-11-12 默认 pytest 在临时 SQLite 数据库升级到 `head`、执行 Alembic `check`、检查三张表、降级到 `base`，测试播种的幂等性、描述补全和冲突保护；知识库接口测试使用假 Embedding/LLM、临时数据库和临时 Qdrant 目录，覆盖两库检索隔离、重复文件、失败重试、客户端和数据库连接重建后检索、重建及删除。

另显式执行 `python -m scripts.smoke_knowledge`，在真实 MySQL 和 Qdrant 本地目录中创建临时知识库，上传文档、按库问答，重建数据库连接与 Qdrant 客户端后再次问答，最后删除临时文档与知识库，结果通过。该命令默认使用假 Embedding/LLM，并关闭 LangSmith 追踪；现已改成每次使用独立随机集合并在结束时删除，不污染正式集合。运行前须停止占用同一 Qdrant 本地目录的 Web 进程。`--live` 才会向 `.env` 配置的模型端点发送演示文本与问题；本轮尝试真实模型时上传在 Embedding 阶段失败，允许联网的重试又因外部数据发送未获明确授权被拦截，因此**没有真实模型通过结论**。运行 `--live` 前须明确同意外发内容及可能费用。

手动上传时曾遇到 503：旧版假模型冒烟误在正式 `qa_chunks` 集合中建立 2 维向量配置，真实 Embedding 的维度与之不符。已在停止 Web 服务后核对该集合只有 0 个点，再仅删除此空集合；用户的 `failed` 文档与原文件保留，可用重建索引接口重试。索引服务现在会对维度不匹配返回明确错误信息，回归测试覆盖这一情况。修正后的冒烟脚本已再次通过，正式集合没有被重新创建。

手动按库问答随后遇到 500：检索已正常，堆栈定位在 `OpenAIChatLLM.generate()`。当前默认模型收到固定 `temperature=0.2` 时返回 400，提示仅支持默认温度。现将温度默认值改为 `None`，普通和流式生成在未显式指定时均不传该参数；离线回归覆盖两种调用。知识库接口对模型 API 错误返回 502 和不含请求正文的提示。修复后全量 `python -m pytest -q` 为 **26 passed**。

用户随后手动重启服务并复测：`smoke.md` 文档在数据库中为 `ready`、对应 1 个片段；`POST /knowledge-bases/{id}/ask` 针对“星河项目什么时候上线？”返回 **2030 年 5 月 18 日**，证据来自该文档的原文片段及稳定片段 ID。重启后仍能查到同一证据；再次上传相同内容返回 409，并指向已存在文档 ID。故单库真实 Embedding、Qdrant、LLM 问答与重启恢复已得到手动验收，但没有据此推断多库隔离、删除或回答质量的系统性指标已通过。
