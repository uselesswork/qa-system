# 第七阶段 多轮对话

> 对应原模块 15 及后续 Web 展示 · [返回项目说明](../README.md) · [上一阶段](第六阶段-问答接口与前端.md) · [下一阶段](第八阶段-答案感知重排.md)

## 一眼看懂本阶段

本阶段让连续追问利用同一会话历史。用户问“它为什么会失败”时，系统先让模型结合历史生成检索查询，再进入原有 RAG 链路；页面按时间顺序显示消息，并把每轮检索依据收在折叠区。会话只在当前服务进程内有效。

| 项目 | 本阶段结果 |
| --- | --- |
| 目标 | 让“它为什么失败”等追问结合之前的问答继续检索 |
| 核心接口 | `POST /chat`，输入 `session_id` 和 `message` |
| 返回 | 回答、改写查询、证据、元数据及会话 ID |
| 记忆位置 | 服务端进程内 `ChatMemory`，最多保留最近 10 轮消息对 |
| 页面能力 | 多轮消息、新建会话、本地显示历史、折叠证据 |

本阶段没有让向量库直接理解代词，而是先根据会话历史把当前追问改写成检索问题，再交给已有的 RAG 主链路。这样“多轮”主要发生在查询理解与会话管理层。

## 具体完成的工作

### 会话记忆与查询改写

`ChatMemory` 以 `session_id` 为键存放用户和助手消息，超出上限时只保留最近消息。`LLMQueryRewriter` 读取最多五轮历史，调用模型生成用于检索的新查询；模型返回空字符串时回退到原问题。`ChatService.chat()` 先取历史并改写，再调用 `RAGCore.answer()`；成功生成回答及结构化证据后，才将用户和助手消息作为完整一轮写入记忆，最后返回 `ChatTurn`。

### Web 接口和页面

`POST /chat` 把 `ChatTurn` 转成适合页面读取的 JSON。页面生成随机会话 ID，发送新问题时保留同一 ID，显示用户与助手消息、等待状态及错误提示。每轮的改写查询和证据放在可折叠区域；“新对话”生成新 ID。浏览器 `localStorage` 保存当前会话 ID 和展示历史，刷新后可看到旧消息。

## 请求与数据流

```text
页面 message + session_id → /chat → ChatMemory.get(session_id)
→ LLMQueryRewriter → RAGCore.answer(rewritten_query)
→ ChatMemory.append_turn(用户消息, 回答) → ChatTurn → 页面展示答案和证据
```

`ChatService.chat()` 在记录当前轮次之前先读取旧历史并改写。RAG 调用或证据转换失败时，本轮不会写入 `ChatMemory`，避免出现只有用户问题、没有助手回答的半轮记录；成功的一轮完成后，下一轮才能看到完整问答。目前没有同一会话并发请求的串行化控制。

## 接口和页面

`POST /chat` 的 JSON 包含 `session_id` 与 `message`；Pydantic 当前只声明二者为字符串，没有限制空串。响应包含 `session_id`、`user_message`、`answer`、`rewritten_query`、`evidence[]` 和 `metadata`。页面生成 UUID；同一对话沿用 ID，“新对话”另生成 ID，但不会删除后端旧会话。

请求形状示例（占位会话 ID，不代表真实模型输出）：

```json
{"session_id":"example-session","message":"它在什么情况下会失败？"}
```

返回中的 `rewritten_query` 供用户核对系统实际检索了什么；`evidence[]` 是当前轮选出的依据，不是整段会话所有引用的集合。下一轮只从同一 `session_id` 读取历史；客户端换 ID 即视为新会话。

前端使用 `localStorage` 保存当前 ID 和最近展示历史，刷新后可重绘消息。请求期间禁用输入，完成或报错后恢复；动态文本以 `textContent` 写入。Enter 发送，Shift+Enter 换行。当前 `localStorage` 只保留当前对话，不提供多个历史会话列表；新对话会清空显示历史。

## 验证与限制

原模块以“定义 → 局限 → 方法对比”的三轮问题观察改写效果，并记录各轮结果；本轮没有真实模型复跑。当前 `/chat` 返回完整结果，不能边生成边显示。服务重启、多进程或多实例时服务端记忆无法共享；浏览器历史只恢复画面，不会把历史重新注入服务端。页面没有账号隔离或同一会话并发请求的服务端锁。
